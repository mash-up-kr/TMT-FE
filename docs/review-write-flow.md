# 리뷰 작성 플로우 설계

> 대상 Figma: [TMT - Main / Dev 섹션 `1028:6900`](https://www.figma.com/design/s9CwH81CeRELOPuoWRISzH/TMT---Main?node-id=1028-6900)
> 관련 브랜치: `feat/#110-review-write-flow`

이 문서는 리뷰 작성 플로우가 **어떤 단계를 거쳐 무엇을 결정하는지**를 남기는 것이 목적이다.
픽셀 스펙은 Figma가 정본이고, 토큰 값은 `src/shared/styles/`가 정본이다. 여기 복제하지 않는다.

구현된 코드가 실제로 **어떤 흐름으로 동작하는지**는
[`review-write-flow-implementation.md`](./review-write-flow-implementation.md)를 본다.

## 단계 개요

| 단계 | 이름 | Figma 프레임 | 필수 | 제안 세그먼트 |
|---|---|---|---|---|
| 1 | 방문 매장 선택 | `리뷰 작성_매장 검색_*` | **필수** | `store` |
| 2 | 사진 등록 | `리뷰 작성_사진 등록_*` | 선택 | `photos` |
| 3 | 태그 선택 | `리뷰 작성_태그_*` | 선택 | `tags` |
| 4 | 별점 + 텍스트 리뷰 | `리뷰 작성_별점/텍스트_*` | 선택 | `rating` |
| — | 완료 | `리뷰 작성_완료_*` | — | `complete` |

세그먼트 이름은 이 문서의 제안이다. 확정 전에 팀 합의가 필요하다.

### 필수/선택 구분 — 이 플로우의 핵심 규칙

`1028:6914`(2단계 Button Stack) 주석:
> `매장 등록 이외에 다른 모든 페이지는 선택사항이기 때문에 기본으로 활성화 상태 설정`

즉 **게이트가 걸리는 단계는 1단계 하나뿐**이다.

- 1단계: 매장이 선택될 때까지 "다음" `disabled`, 타이틀 아래 **"필수" 뱃지** 노출
- 2~4단계: "다음" 항상 `enabled`, 뱃지 대신 **안내 문구** 노출 —
  `정보를 입력하면 그룹에 가입할 수 있는 티켓을 드려요` (`Icon/alert-circle` + `body-md`, `label-tertiary`)

따라서 2~4단계에는 입력값 유효성 게이트를 만들지 않는다. 만들면 시안과 어긋난다.

### 프로그레스 값 규칙

각 단계 프레임의 Progress Bar 실측값:

| 화면 | 인디케이터 | 완료 수 |
|---|---|---|
| 1단계 매장 (`1357:62630`) | `percentage=0`, `right-full` | 0 |
| 2단계 사진 (`1028:6905`, 주석 `프로그래스바 2단계`) | `right-3/4` = 25% | 1 |
| 3단계 태그 | `percentage=50`, `right-1/2` | 2 |
| 4단계 별점·텍스트 (`1340:38680`) | `percentage=75`, `right-1/4` | 3 |

**프로그레스는 "현재 단계"가 아니라 "완료한 단계 수"다.** `value` = 완료 수, `max` = 4.
2단계 화면에서 25%라는 실측이 이 규칙을 확정한다 — 현재 단계 인덱스라면 50%여야 한다.
완료 화면에는 Progress Bar가 없다(`Main Content`만 존재).

### 단계 간 이동과 상태 보존

3단계 프레임 주석:
> `뒤로가기 버튼 클릭시 사용자가 이전에 작성했던 내용 보존`

2단계부터 GNB **좌측에 뒤로가기**, 우측에 닫기(X)가 있다. 1단계 GNB에는 닫기만 있다.
뒤로 이동해도 입력값이 살아 있어야 하므로, **초안 상태는 단계 컴포넌트가 아니라 플로우 전체가 소유**해야 한다.

## 라우팅 설계

```
/reviews/new/store      1단계 — 매장(+주소) 선택   필수
/reviews/new/photos     2단계 — 사진 최대 3장      선택
/reviews/new/tags       3단계 — 태그 복수 선택     선택
/reviews/new/rating     4단계 — 별점 + 텍스트      선택
/reviews/new/complete   완료
```

### 왜 스텝을 URL에 드러내는가

단일 라우트에 로컬 state로 단계를 숨기는 방식을 쓰지 않는다. 이유는 세 가지고, 첫 번째가 결정적이다.

1. **뒤로가기가 "이전 단계"여야 한다.** 시안에 뒤로가기 버튼이 명시돼 있고 "이전 내용 보존"까지 요구된다.
   단일 라우트면 안드로이드 하드웨어 백과 iOS 스와이프 백이 플로우 전체를 이탈시킨다.
2. 단계별 딥링크와 이탈 지점 추적이 가능하다.
3. 단계마다 `page.tsx`가 갈려 코드 분할과 변경 경계가 자연스럽다.

Shopify 체크아웃(`/information` → `/shipping` → `/payment`), Stripe 온보딩이 같은 형태다.

### 왜 `[step]` 동적 세그먼트가 아니라 명시적 세그먼트인가

`[step]`은 URL로 임의 문자열이 들어오므로 경계에서 런타임 검증이 필요하다
(`.claude/rules/conventions.md` — user input은 경계에서 검증). 명시적 세그먼트는 그 부담이 없다.

### 왜 `reviews` 복수형인가

REST 리소스 명명 관례를 따른다. `/reviews`(목록) · `/reviews/new`(작성) · `/reviews/[id]`(상세).
이 레포의 첫 도메인 라우트라 여기서 선례가 정해진다.

### layout이 무엇을 소유하는가

App Router의 layout은 **자식 라우트 간 이동에서 리마운트되지 않는다.** 이게 이 구조를 택한 기술적 근거이고,
"뒤로가기 시 내용 보존" 요구를 별도 저장소 없이 만족시키는 방법이다.

```
src/app/reviews/new/
├── layout.tsx          GNB + Progress + 초안 상태 provider + 닫기 모달
├── _constants/         단계 정의 — 세그먼트, 순서, 총 단계 수
├── _components/
├── store/page.tsx      1단계
├── photos/page.tsx     2단계
├── tags/page.tsx       3단계
├── rating/page.tsx     4단계
└── complete/page.tsx   완료
```

- Progress·GNB·닫기 모달은 모든 단계가 공유하므로 layout이 소유한다.
  현재 단계는 `usePathname()`으로 판별하고, 단계 정의는 `_constants/`에 한 벌만 둔다.
- **초안 상태 provider를 layout에 둔다.** 이전 문서에서는 "단계가 하나뿐이라 보류"였으나,
  4단계 전부와 "뒤로가기 보존" 요구가 확인됐으므로 지금은 소비자가 명확하다.
- 완료 화면은 Progress·GNB 뒤로가기가 없다. layout 안에 두되 단계 UI를 숨기거나,
  `new` 바깥의 별도 라우트로 뺀다 — **미결 사항 2번**.

## 1단계 — 방문 매장 선택

### 화면 구성

| 영역 | 내용 | 재사용 |
|---|---|---|
| GNB | "리뷰 쓰기" 중앙, 우측 닫기(X) | `shared/ui/GNB` + `IconButton` + `CancelIcon` |
| Progress | 0/4 완료 | `shared/ui/Progress` |
| 타이틀 | "방문한 매장,\n어디였나요?" | `text-heading-lg` |
| 뱃지 | "필수" | **신규** (아래 참고) |
| 검색 | "매장명을 검색해보세요" | `shared/ui/TextField/SearchField` |
| 주소 필드 | 직접 입력 분기에서만 노출 | `shared/ui/TextField` |
| CTA | "다음" | `shared/ui/ButtonStack` + `Button` |

### 매장 검색 — 바텀시트로 확정

이전 문서의 "인라인인지 바텀시트인지" 미확인은 해소됐다. **바텀시트다.**

- 검색 필드를 누르면 Scrim + Bottom sheet가 올라온다. 시트 GNB 좌측 타이틀 "매장 검색", 우측 X.
- 시트 안에 검색 입력(값 있으면 우측 clear 아이콘) + 결과 Option group + iOS 키보드.
- 결과 행 하나 = **매장명(body-lg) + 주소(body-md, tertiary)** 2줄.
- Scrim 주석: `딤드 화면 클릭시 바텀시트 자동 out`.
- **시트 높이는 내용과 무관하게 고정이다.** 결과 3행(`1357:62202`)·결과 0건(`1357:62184`)·
  주소 검색 Intro(`1357:62728`) 세 프레임 모두 720/780이다.

### 결과 0건과 직접 입력 — 이 단계의 두 번째 경로

결과 목록 **맨 아래에는 항상** `'{검색어}' 직접 입력하기` 옵션이 붙는다(primary 색 텍스트).
결과 0건 화면(`1357:62184`)은 이 옵션 하나만 남은 상태다.

주석 (`Option_직접입력`):
> `매장 검색시 검색항목 0건일 때 매장명 직접 입력하기 버튼을 클릭하면 매장 수동 입력 가능`
> `매장 주소 수동 입력 페이지로 이동`

주소 필드 주석:
> `['매장명' 직접 입력하기] 버튼 클릭시 매장명이 직접 입력되고 아래로 주소 검색창 활성화`
> `클릭하면 주소 검색_Intro 바텀시트 등장`

즉 1단계 안에 상태 분기가 둘 있다. **둘 다 progress는 0이고 같은 라우트다.**

```
                          ┌─ 결과 선택 ──────────────→ selectedStore = { 검색결과 매장 }
검색어 입력 → 결과 조회 ──┤
                          └─ '직접 입력하기' 선택 ──→ 매장명 확정 + 주소 필드 노출
                                                        ↓
                                          주소 필드 클릭 → 주소 검색 바텀시트
                                          ("건물, 지번, 도로명을 입력해 주세요")
                                                        ↓
                                          결과 행 = 도로명/지번 뱃지 2줄
                                                        ↓
                                          주소 선택 → selectedStore = { 이름 + 주소 }
```

주소 검색 결과 행은 한 행에 **`도로명` 뱃지 + 도로명 주소**, **`지번` 뱃지 + 지번 주소** 두 줄을 함께 보여준다.

주소 검색 바텀시트의 Intro(`1357:62728`)에는 검색 필드 아래 **검색 팁**이 있다.
`이렇게 검색해 보세요` (body-md-bold, label-secondary) + 불릿 3줄 (body-md-regular, label-tertiary):
도로명 + 건물번호 (위례성대로 2) · 건물명 + 번지 (방이동 44-2) · 건물명, 아파트명 (반포 자이, 분당 주공 1차).
매장 검색 시트에는 이에 대응하는 안내가 없다.

### "다음" 활성화

Figma 주석: `매장 입력 전까지 해당 버튼 disabled`.

게이트 조건은 **검색어 문자열이 아니라 "선택된 매장 객체의 존재"**로 잡는다.
검색어가 있어도 매장을 고르지 않았으면 다음 단계로 넘길 데이터가 없기 때문이다.
직접 입력 경로에서는 **매장명과 주소가 모두 확정된 시점**에 객체가 완성된다.
따라서 게이트는 두 경로 모두에 대해 하나의 조건으로 표현된다.

### 다뤄야 할 상태

- **loading** — 검색 API 응답 대기
- **empty** — 결과 0건. 직접 입력 옵션만 남음 (경로가 끊기지 않음)
- **error** — 검색 실패
- **disabled** — 매장 미확정 시 "다음"
- **selected** — 검색 필드에 확정된 매장명이 채워진 상태(`state=Filled`, clear 아이콘 노출)

## 2단계 — 사진 등록

| 영역 | 내용 |
|---|---|
| 타이틀 | "그날의 순간,\n사진으로 남겨볼까요?" |
| 안내 | `정보를 입력하면 그룹에 가입할 수 있는 티켓을 드려요` |
| 업로드 영역 | 점선 테두리 placeholder, `Icon/plus` + `0/3` 카운터 |
| CTA | "다음" (항상 활성) |

주석:
- `해당 영역 클릭시 사진 첨부 가능`
- 카운터: `첨부된 사진 개수 표시 필요`

**최대 3장.** 시안은 0장/1장/2장 세 상태를 제공한다.

- 첨부된 사진은 120×120 썸네일, 우상단 `Icon/x-circle`로 개별 삭제
- placeholder는 썸네일 **오른쪽에** 남아 있고 카운터가 `1/3` → `2/3`으로 갱신
- 3장이 되면 placeholder가 사라지는지는 시안에 없다 — **미결 사항 3번**
- 2장 상태의 Image Container 폭이 376px로 화면(320px)을 넘는다 → **가로 스크롤 컨테이너**로 읽는다

## 3단계 — 태그 선택

| 영역 | 내용 |
|---|---|
| 타이틀 | "어떤 자리였어요?" |
| 안내 | 2단계와 동일 문구 |
| 태그 그룹 1 | 라벨 "누구와 함께했나요? (복수 가능)" — 혼자 / 연인 / 친구 / 동료·지인 / 가족 |
| 태그 그룹 2 | 라벨 "어떤 점이 좋았나요? (복수 가능)" — 음식이 맛있어요 / 응대가 친절해요 / 분위기가 좋아요 / 가성비가 좋아요 / 청결하고 깔끔해요 / 교통이 편리해요 / 자리가 넓고 편해요 |
| CTA | "다음" (항상 활성) |

주석:
- `여러개 선택 가능, 전부 선택도 가능` — 상한 없음. 최소 선택 수도 없다(선택 단계이므로)
- `해당 페이지도 선택 페이지, 버튼 활성화`
- `뒤로가기 버튼 클릭시 사용자가 이전에 작성했던 내용 보존`

두 그룹은 서로 독립적인 다중 선택이다. 칩은 기존 `shared/ui/Chip`의 `selected`/기본 상태로 표현된다.
그룹이 두 개이므로 `_constants/`에 **그룹 정의(라벨 + 옵션 목록)** 를 데이터로 두고 렌더는 한 벌로 처리한다.

## 4단계 — 별점 + 텍스트 리뷰

| 영역 | 내용 |
|---|---|
| 타이틀 | "이번 방문,\n어떠셨어요?" |
| 안내 | 2단계와 동일 문구 |
| 별점 | 라벨 "방문에 만족하셨나요?" + `Icon/star` 5개 (각 44×44) |
| 텍스트 | 라벨 "리뷰를 작성해 주세요" + 우측 카운터 `0/500` |
| 입력 | placeholder "어떤 점이 좋았나요? 편하게 남겨주세요", 최소 높이 180px |
| CTA | "다음" (항상 활성) |

- 별점은 5점 척도. 44×44는 터치 타깃 기준을 만족한다(`design-system.md`).
- 텍스트는 **최대 500자**. 카운터가 현재 길이를 표시한다.
- 텍스트 영역 우하단에 리사이즈 grabber가 그려져 있으나, 모바일 전용 웹앱에서 실제로 동작할지는
  구현 시 판단한다(시안상의 기본 `<textarea>` 표현일 가능성이 높다).

## 완료 화면

| 영역 | 내용 |
|---|---|
| 문구 | "리뷰 작성이\n완료되었어요!" (중앙 정렬) |
| 매장 | `Icon/map-pin` + 매장명 (primary 색) |
| 비주얼 | 240×240 — **사진형**(등록한 사진 220×220) / **일러스트형** 두 벌 |
| CTA | 좌 "홈으로 가기"(secondary) · 우 "다른 리뷰 보러가기"(primary) |

두 벌이 존재하는 이유는 2단계에서 **사진을 등록했는지 여부**로 갈리는 것으로 읽는다.
사진이 있으면 첫 장을, 없으면 일러스트를 보여준다. 이 해석은 시안 구조에 근거하지만 주석으로 명시돼 있진 않다.

Progress Bar와 뒤로가기가 없다. 완료 후 뒤로가기로 4단계에 돌아가지 못하게 하는 처리가 필요하다
(`router.replace`).

## 작성 중 이탈 — 확인 모달

이전 문서의 미확인이 해소됐다. `리뷰 작성_닫기`(`1046:15263`) 프레임에 모달이 있다.

모달 주석: `상단 닫기 버튼 클릭 시 리뷰 작성 중단 안내 모달 제공`

| 요소 | 값 |
|---|---|
| 제목 | "리뷰 작성을 그만두시겠어요?" |
| 본문 | "지금까지 입력한 내용이 모두 삭제돼요." |
| 좌 버튼 | "나가기" (secondary) — 초안 폐기 후 이탈 |
| 우 버튼 | "계속 작성하기" (primary) — 모달만 닫음 |

**초안은 임시 저장하지 않는다.** 본문이 "모두 삭제돼요"라고 단언하므로 localStorage 복원 같은 장치를 넣으면
문구와 모순된다.

모달은 2단계 프레임 위에 그려져 있지만, X는 모든 단계 GNB에 있으므로 **layout이 모달을 소유**한다.
1단계 진입 직후처럼 입력이 하나도 없을 때도 모달을 띄울지는 시안에 없다 — **미결 사항 4번**.

X를 눌렀을 때의 이동 대상은 1단계 주석 기준 `사용자가 경험하던 이전 화면으로 이동`이다.

## 컴포넌트 결정

`.claude/rules/design-system.md`의 결정 순서(기존 사용 → 조합 → variant 추가 → 신규)를 따른 결과.

**그대로 재사용** — `GNB`, `IconButton`, `Progress`, `SearchField`, `TextField`, `ButtonStack`, `Button`,
`Chip`, `BottomSheet`, `Toast`

**검토 필요**

| 대상 | 판단 |
|---|---|
| "필수" 뱃지 | `Chip`의 `selected` 색과 정확히 일치하나 `Chip`은 `<button>`이다. 누를 수 없는 정적 라벨이므로 그대로 쓰면 동작하지 않는 버튼이 접근성 트리에 노출된다. → 라우트 로컬 컴포넌트로 시작 |
| 주소 결과의 `도로명`/`지번` 뱃지 | 위 "필수" 뱃지와 같은 형태(작은 pill 라벨). **두 번째 사용처가 확인됐으므로** `shared/ui/Badge` 승격을 검토할 근거가 생겼다 |
| 검색 결과 Option group | 매장 검색(2줄)·주소 검색(뱃지 2줄)·직접입력(1줄 강조)로 변형이 셋이다. 바텀시트 안에서만 쓰이는 목록이므로 라우트 로컬로 두고, 행 렌더만 분기한다 |
| 사진 썸네일 + 삭제 | 신규. 라우트 로컬 |
| 별점 입력 | 신규. 읽기 전용 별점(리뷰 목록 등)과 입력용 별점이 갈릴 수 있으므로 이번엔 입력용만 로컬로 만든다 |

## 구현 현황

```
src/app/reviews/new/
├── layout.tsx                    ReviewFlowShell 위임
├── page.tsx                      /store로 redirect
├── _constants/steps.ts           4단계 정의
├── _model/store.ts               ReviewStore · 검색 결과 타입
├── _utils/reviewStore.ts         "다음" 게이트 판정
├── _stores/ReviewDraftProvider   초안 상태 (현재 store만)
├── _components/                  Badge · ExitConfirmModal · SearchOptions
│                                 StoreSearchSheet · AddressSearchSheet · ReviewFlowShell
└── store/page.tsx                1단계
```

매장·주소 검색과 태그는 생성된 mock API를 사용한다. API 응답은 라우트 utility에서 시트와 태그 UI가
쓰는 모델로 변환한다.

결과 행 컴포넌트는 도메인 필드가 아니라 시안이 그리는 줄 단위(`primary`/`secondary`)로 props를 받는다.
서버 필드 이름이 달라져도 호출부 매핑만 고치면 된다.

리뷰 제출 endpoint는 현재 OpenAPI에 없으므로, 완료 화면은 초안을 보여주기만 한다.

## 미결 사항

구현 전에 답이 필요한 순서대로.

0. **바텀시트 높이의 기준 — 디자이너 확인 필요. 이 플로우를 완료 처리하기 전에 반드시 답을 받는다.**
   시트는 720, 프레임은 780이라 92%지만, 그 780에는 상태바(44)와 Safari 크롬(133)이 포함돼 있다.
   웹이 쓰는 뷰포트(603) 기준으로 다시 재면 587/603 = **97%**다. 같은 시안이 기준에 따라 92%도
   97%도 된다. 현재 구현은 92%(`--layout-sheet-height: 92dvh`)를 쓰지만 그 선택의 근거가
   기록된 적이 없다. 함께 확인할 것: iOS Safari에서 키보드가 올라올 때 고정 높이 시트의 하단이
   가려지는지. 상세는 `review-write-flow-implementation.md` §9.4.
1. **완료 화면의 위치** — `reviews/new/complete`로 두고 layout에서 단계 UI를 숨길지,
   `reviews/complete` 등 플로우 밖으로 뺄지.
   → 구현은 **플로우 안**으로 갔다. 매장명·사진을 보여주려면 초안이 살아 있어야 하고, 초안은
   이 layout의 provider가 소유한다. 밖으로 빼면 사진(object URL)이 언마운트와 함께 사라진다.
2. **사진 3장을 채웠을 때** placeholder를 숨기는지. 시안에 3장 상태가 없다.
   → 구현은 **숨기는 쪽**으로 갔다(`PhotoPicker`). 더 담을 수 없는데 버튼이 남으면 누를 수 있는
   것처럼 보이기 때문이다. 디자이너 확인 필요.
3. **입력이 없는 상태에서 X**를 눌러도 확인 모달을 띄우는지.
4. **완료 화면 비주얼 분기 기준** — 두 벌(마스코트 220 / 매장 일러스트 240) **모두 고정 브랜드
   에셋**이다. `1028:7062`의 레이어 이름이 `KakaoTalk_Photo_…`라 사용자가 올린 사진처럼 보이지만
   아니다. 지금은 사진 유무로 갈라 두었으나 근거가 없다 — **언제 무엇을 쓰는지 디자이너 확인 필요.**
5. **세그먼트 이름 확정** — `store` / `photos` / `tags` / `rating` 제안.
6. **칩 아이콘 12종 익스포트 요청** — 3단계 태그 칩에 붙는 20×20 컬러 일러스트
   (혼자·연인·친구·동료지인·가족 / 음식·응대·분위기·가성비·청결·교통·자리).
   Figma에서 조각으로만 내려와 통째로 받을 수 없어 **현재 구현은 텍스트 칩만** 있다.
   SVG 12개를 받으면 태그 응답과 매핑하는 UI metadata에 `icon` 필드만 더하면 된다.
7. **규칙 해석 합의** — `reviews/new/store/page.tsx`가 `reviews/new/_components/`를 import하는 것이
   architecture rule의 "다른 라우트의 private segment import 금지"에 걸리는지.
   `reviews/new/**` 서브트리를 하나의 라우트로 보는 해석을 제안한다. 대안(단계마다 `_components` 중복)은
   명백히 더 나쁘다. 팀 합의 필요.
