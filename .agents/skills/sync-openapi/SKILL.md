# sync-openapi — 스펙에서 훅까지, 한 번에

백엔드가 API를 바꿨을 때 프론트에서 해야 할 일 — 스펙 받기, 생성, 무엇이 바뀌었는지 파악, 깨진 곳 찾기, 검증 — 을 한 번에 처리한다.

## 두 가지 설계 원칙

1. **스펙이 정본이다.** 이 스킬은 endpoint를 하나도 모른다. 스펙에 있는 것만 생성되고, 스펙에 없는 것은 프론트에서 만들지 않는다.
2. **깨진 곳을 먼저 알린다.** 생성은 성공해도 호출부가 깨질 수 있다. typecheck 결과를 그냥 흘리지 않고, 무엇이 왜 깨졌는지 스펙 변경과 연결해 보고한다.

## 레포 규약 (정본: `.claude/rules/architecture.md`의 API 계약)

- 생성물은 `src/api/gen/`이며 **직접 수정하지 않는다**.
- 스펙 스냅샷은 `_scripts/api/openapi.json`이며 이 명령이 갱신한다. 직접 편집하지 않는다.
- 생성물과 스냅샷은 **커밋한다**.
- mock layer는 도입하지 않았다. 백엔드에 없는 endpoint를 mock으로 채우지 않는다.

## 워크플로우

### 1 — 선행 조건 확인

`TMT_OPENAPI_URL`이 필요하다. `.env`에 없으면 `pnpm env:sync`를 안내한다 (Infisical `dev` 환경에서 내려온다).

스펙 서버에 닿을 수 없는 상황이라면, 기존 스냅샷만으로 생성할 수 있다는 것을 알린다: `pnpm exec orval`. 이때는 스펙이 갱신되지 않으므로 **"스펙은 그대로, 설정 변경만 반영"** 임을 명시한다.

### 2 — 변경 전 스냅샷 보관

diff 요약을 위해 현재 `_scripts/api/openapi.json`의 endpoint 목록(`method + path`)을 먼저 읽어둔다. 파일이 없으면 최초 생성이다.

### 3 — 생성

```
pnpm api:sync
```

실패하면 스크립트가 원인별로 안내한다 (URL 없음 / 401·403 / 타임아웃 / JSON 아님 / 빈 스펙). 임의로 우회하지 말고 안내대로 처리한다.

### 4 — 무엇이 바뀌었는지 요약

새 스냅샷의 endpoint 목록과 2단계 목록을 비교해 보고한다.

- **추가된 endpoint** — 어느 태그(=컨트롤러)에 붙었는지
- **삭제된 endpoint** — 호출부가 있으면 반드시 깨진다
- **시그니처 변경** — 응답 타입, 필수 파라미터, 필드 optional 여부

`git diff --stat src/api/gen`으로 생성물 변경 규모를 함께 보여준다.

### 5 — 깨진 호출부 찾기

삭제·변경된 operation의 생성 함수명(`use<OperationId>`, `get<OperationId>QueryKey` 등)을 `src/app/`에서 검색해 사용처를 나열한다. **typecheck를 돌리기 전에** 이 목록을 먼저 보고한다 — 사용자가 영향 범위를 미리 알 수 있다.

### 6 — 검증

```
pnpm check && pnpm typecheck
```

`pnpm build`는 생략하고 생략했다고 밝힌다. 생성 코드 변경은 타입 경계 문제가 대부분이라 typecheck에서 잡히고, build는 느리다. 라우트 코드까지 함께 고쳤다면 `pnpm verify`를 돌린다.

typecheck가 깨지면 **생성물을 고치지 않는다.** 고칠 곳은 호출부다. 스펙 자체가 잘못됐다고 판단되면 백엔드에 알릴 내용을 정리해 보고한다.

### 7 — 커밋 제안

커밋은 사람이 결정한다. 메시지만 제안한다.

- 스펙 동기화만: `chore: API 스펙 동기화`
- 호출부 수정까지 포함: 수정 성격에 맞는 type을 쓰고 스펙 동기화와 분리할지 물어본다

## 자주 나오는 상황

**생성물 diff가 수천 줄이다** — 정상이다. `clean: true`라 태그 이름이 바뀌면 파일이 통째로 교체된다. 리뷰는 `_model/` 타입 변경에 집중하도록 안내한다.

**태그 이름이 `xxx-controller`다** — 백엔드가 `@Tag`를 붙이지 않으면 springdoc이 클래스명에서 태그를 만든다. 동작에는 문제없다. 파일명을 정리하고 싶으면 백엔드에 `@Tag` 부착을 요청한다 — 프론트에서 스펙을 후처리하지 않는다.

**mock 데이터가 필요하다** — 이 레포는 mock layer를 도입하지 않았다. architecture rule의 Mock 정책을 먼저 합의해 수정해야 한다. 임의로 handler를 만들지 않는다.
