# reuse-scope — 사용처가 승격을 증명한다

architecture rule 2번("라우트 전용 코드가 두 곳 이상에서 쓰이면 `shared/` 승격을 검토한다")은 사람이 눈으로 지키기 어렵다.
라우트가 늘어날수록 같은 코드가 조용히 두 번째·세 번째로 복사되고, 반대로 아직 한 곳에서만 쓰는 코드가 성급하게 `shared/`로 올라간다.
이 스킬은 그 판단을 **감이 아니라 사용처 집계**로 바꾼다.

## 세 가지 설계 원칙

1. **승격은 사용처가 증명한다.** "나중에 또 쓸 것 같다"는 승격 근거가 아니다. 서로 다른 라우트 2곳이 실제로 import하고 있을 때만 [승격]이라고 말한다. 근거가 약한 것은 등급을 낮춰 사람에게 넘긴다.
2. **보고까지만 한다.** 파일을 옮기지도, import를 고치지도, 문서를 만들지도 않는다. 승격은 되돌리기 번거로운 구조 변경이고, 목적지(`shared/ui` vs `shared/components`)는 도메인 판단이 섞인다. 판단과 실행은 사람 몫으로 남긴다.
3. **규칙은 옮겨 적지 않고 읽는다.** 계층 정의와 import 경계의 정본은 `.claude/rules/architecture.md`다. 이 스킬은 규칙을 복제하지 않고 매번 읽어서 적용한다. 그래야 구조 규칙이 바뀌어도 스킬이 낡지 않는다.

## 1 — 범위를 정한다

시작 전에 `.claude/rules/architecture.md`를 읽는다. 허용 구조, 세그먼트 책임, import 경계가 판정 기준이다.

- **대상을 지정했으면** 그것이 범위다 (파일·폴더·컴포넌트 이름).
- **지정하지 않았으면** 브랜치 작업분 전체를 범위로 잡는다:

```bash
git diff --name-only "$(git merge-base develop HEAD)"...HEAD
git status --porcelain   # 미커밋 변경 합침
```

`src/api/gen/**`은 orval 생성물이라 제외한다. 범위에 `src/` 파일이 하나도 없으면 그 사실을 말하고 끝낸다.

## 2 — 심볼과 사용처를 모은다

범위 파일에서 밖으로 공개된 것만 후보다. 파일 내부에서만 쓰는 것은 승격 대상이 아니다.

```bash
rg -n '^export ' <파일>                      # 후보 심볼 추출
rg -n --glob 'src/**/*.{ts,tsx}' -w '<심볼>' src   # 전역 사용처
```

세는 단위는 **파일이 아니라 라우트**다. `src/app/<route>/_*/…`는 그 라우트, `src/shared/**`는 shared, `src/app/(group)/…`는 그 group으로 환산한다.
같은 라우트 안에서 여러 파일이 쓰는 것은 여전히 1곳이다 — 라우트 내부 재사용은 `_components/`의 정상 동작이지 승격 신호가 아니다.

`shared/` 안에서도 경계를 본다. 신호는 **위치**가 아니라 **reach-in 여부**다: 계열 A의 폴더(`shared/ui/A/`) 안에 있는 코드를 계열 B가 직접 import하면 그건 A가 B에게 자기 내부를 내준 것이라 경계 위반이다.
반대로 여러 계열이 함께 쓰는 기반이 처음부터 `shared/ui/` 최상위의 독립 폴더(계열 누구의 하위도 아닌 형제)에 있다면, 그건 architecture rule이 요구하는 정상 배치다 — 예를 들어 `FieldFrame/`이 `TextField/`·`Select/`와 나란히 `shared/ui/` 밑에 있고 둘 다 그것을 쓰는 상태는 이미 옳게 승격되어 있는 것이지 새로 옮길 대상이 아니다.

```bash
rg -n '@/shared/ui/[A-Za-z]+/' src/shared/ui   # 다른 계열 폴더 경로를 직접 import하는지 (reach-in)
```

경로가 계열 폴더 안을 가리키는데 import한 파일이 그 계열 소속이 아니면 위반이고, 경로가 애초에 계열 하위가 아닌 독립 폴더면 위반이 아니다 — 실제로 그 코드가 어느 폴더 밑에 있는지 열어서 확인한다.

상대경로 import(`../../`)로 경계를 넘는 경우가 있으니 심볼 이름 기준 검색을 신뢰하고, 이름이 흔한 경우(`Item`, `Card`)만 파일을 직접 열어 확인한다.

사용처를 주장할 때는 등급과 무관하게 항상 `rg` 결과의 `file:line`을 그대로 인용한다. "TextField와 Select가 함께 쓴다"처럼 폴더·컴포넌트 이름만으로 뭉뚱그리지 않는다 — 이미 정상 배치라 승격할 게 없다는 결론일 때도 그 결론을 뒷받침하는 import 지점은 똑같이 `file:line`으로 밝힌다. 근거가 검증 가능해야 보고를 신뢰할 수 있다.

## 3 — 중복과 경계를 확인한다

**중복** — 범위에서 새로 만든 것이 이미 `shared/`에 있는지 본다. 이름이 달라도 역할이 같으면 중복이다(`Dropdown`↔`Select`, `Spinner`↔`LoadingIcon`, `Tag`↔`Chip`, `formatDate`↔기존 포맷터).

```bash
ls src/shared/ui src/shared/components src/shared/hooks src/shared/utils
```

**경계** — 승격 여부와 무관하게 rule 위반은 즉시 보고한다.

```bash
rg -n "@/app|\.\./\.\./app" src/shared src/api   # shared·api → app 역방향
rg -n "@/api" src/shared/ui                       # shared/ui → api
rg -n "@/app/" src/app                            # 라우트 간 직접 import — alias 경로
rg -n 'from "\.\./\.\./' src/app                  # 라우트 간 직접 import — 상대경로. 매치마다 실제로 다른 라우트를 가리키는지 확인 (깊이 중첩된 같은 라우트 내부 이동은 위반 아님)
```

## 4 — 판정한다

| 등급 | 조건 | 결론 |
|---|---|---|
| `[중복]` | `shared/`에 같은 역할이 이미 있는데 라우트에서 새로 만듦 | 새로 만들지 말고 기존 것을 쓰거나 확장한다 |
| `[승격]` | 서로 다른 라우트 2곳 이상이 사용 | rule 2 — 승격 검토. 도메인 무관하면 `shared/ui/`, 도메인 성격이 남으면 `shared/components/` |
| `[경계]` | import 방향 위반, 또는 계열 폴더(`shared/ui/A/`) 안의 코드를 다른 계열이 직접 import(reach-in) | 승격과 별개로 지금 고쳐야 한다. reach-in이면 해당 코드를 계열 하위가 아니라 `shared/ui/`의 공통 상위 독립 폴더로 옮긴다 |
| `[관찰]` | 사용처는 1곳이지만 공통화 신호가 있음 — 도메인·API·라우트에 묶이지 않은 UI primitive거나 순수 함수, 또는 기존 `shared/ui` 계열과 형태가 겹침 | 지금 올리지 말고 두 번째 사용처가 생길 때 재검토. rule 4의 예외(도메인 무관 primitive, 전역 토큰, provider)에 해당하면 그 근거를 함께 적는다 |
| `[보류]` | 1곳 사용 + 신호 없음 | 그대로 둔다 |

[보류]는 이 스킬의 기본값이다. 대부분의 라우트 코드는 그 라우트에 있는 것이 맞고, 성급한 공통화는 나중에 되돌리기가 더 비싸다.
등급을 올릴지 망설여지면 낮은 등급에 두고 무엇이 확인되면 올라가는지 한 줄로 적는다.

## 5 — 보고한다

기본은 짧은 브리프다. 사람이 스캔하고 바로 판단할 수 있어야 한다.

```
## 승격 검토: <범위>

### [중복] <심볼>
- `<file>:<line>` → 기존 `<shared 경로>`
- 근거: <같은 역할인 이유>

### [승격] <심볼>
- `<file>:<line>` · 사용처: `<route A>`, `<route B>`
- 권장: `src/shared/<ui|components>/<이름>`
- 근거: <도메인 무관/도메인 성격 판단>
- (UI 컴포넌트라면) 참고: <하드코딩된 color·spacing·radius 값이 있으면 한 줄로 남긴다. `.claude/rules/design-system.md`가 정본이며, 승격 여부 자체를 바꾸진 않지만 옮기기 전에 토큰으로 바꿀지 검토할 거리다.>

### [경계] <위반>
- `<file>:<line>` — <어떤 방향 위반인지>

### [관찰] <심볼>
- `<file>:<line>` · 사용처: `<route A>` 1곳
- 신호: <왜 공통화 후보인지> / 조건: <무엇이 생기면 승격>

### 탐색 한계
- <본 범위와 안 본 것>
```

- 해당 등급이 없으면 그 절을 지운다. 빈 제목만 남기지 않는다.
- 후보가 하나도 없으면 "승격·중복 후보 없음"이라고 분명히 말하고, 무엇을 어디까지 봤는지 남긴다. 억지로 항목을 만들지 않는다.
- `[보류]`는 개별 나열 대신 마지막에 "나머지 N개는 1곳 사용, 현 위치 유지"로 묶는다.
- **탐색 한계는 항상 쓴다.** 이름 기반 검색이라 동적 참조나 재export를 놓칠 수 있고, 아직 없는 라우트의 미래 사용은 알 수 없다. 무엇을 확인하지 못했는지 밝혀야 보고를 신뢰할 수 있다.

**"자세히"라고 하면** 각 [승격]·[중복] 항목에 옮길 파일 목록, 새 경로, 고쳐야 할 import 지점, 안 올렸을 때 생길 문제(같은 코드의 세 번째 복사본 등), 올렸을 때의 리스크(도메인 타입이 `shared/ui`로 새는 등)를 덧붙인다. 그래도 코드는 건드리지 않는다.

## 하지 않는 것

- 파일 이동, import 수정, 코드 작성. 이 스킬의 산출물은 보고뿐이다.
- 범위 밖 전 레포 중복 감사. 범위는 변경분(또는 지정 대상)이고, 전체 감사는 다른 작업이다.
- 문서 파일 생성. 결과는 대화로만 전달한다.
- 스타일·네이밍·성능 지적. 그건 코드 리뷰의 일이고 여기서는 노이즈다.
